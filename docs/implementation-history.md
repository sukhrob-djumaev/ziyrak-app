## Phase 1 implementation record

### Implementation record (Phase 1 complete)

Phase 1 is implemented and complete. This is a record of concrete findings from that implementation, not a revision to the architecture above.

- Final schema carries mandatory tenant ownership (`businessId NOT NULL`, FK, index) on every table in §12, plus every composite `@@unique`/composite FK from §8.4's table.
- `src/lib/default-business.ts` is a **temporary compatibility layer**, introduced because the existing application still needs to operate against the Default Business until Phase 2 introduces real `TenantContext` resolution. It is transitional and **owned by Phase 2 for removal/replacement** — Phase 2 should delete it, not extend it, as each call site is converted to explicit `ctx`.
- API-key authentication (`route-auth.ts`'s `authenticateApiKey()`) currently fails closed, since the plaintext `key` column it used to query no longer exists. Phase 2 task 9 wires the real `keyPrefix`+`keyHash` authentication path.
- `Settings.aiApiKey` remains in the retained legacy `Settings` row — Phase 1 has no defined final destination for it. Phase 4 must migrate it once the AI provider configuration boundary (`AIProviderRegistry`) becomes real.
- Legacy `Channel` rows were migrated into `ChannelConnection` by combining each channel's existing status with its corresponding `Settings` credentials/configuration (not itself a named §13.2 step, but the only coherent reading of §7.7).
- `BusinessHours` was backfilled in place (same `"default"`-id row) rather than duplicated into a new row, since that is the implementation compatible with its final `NOT NULL` + `@@unique([businessId])` tenant ownership.
- `ToolPolicy`, `ActionExecution`, and `InboundEventReceipt` were intentionally not created in Phase 1 — despite appearing in §12's full target-model table, their implementation phases are Phase 6/5, not §46.1's own task list.
- Phase 1 remains explicitly **unsafe for real external multi-tenant onboarding** until Phase 2 completes authentication, tenant resolution, scoped Prisma access, and route-level enforcement.

## Phase 2 implementation record

### Implementation record (Phase 2 complete)

Phase 2 is implemented and complete. This is a record of concrete findings from that implementation, not a revision to the architecture above.

- `TenantContext`/`ExecutionPrincipal` (§8.2/§9.5), the tenant-scoping Prisma Client Extension (§8.3), `assertSameTenant()` (§8.5), `resolveTenantPlacement()`/`getDataPlaneClient()` (§7.5/§28.2), and the raw-client ESLint restriction (§8.3/§16.4) are all implemented in `src/lib/tenancy/**`. The restriction covers both static and dynamic (`await import(...)`) raw-client imports — the latter was found, empirically, not to be caught by `no-restricted-imports` alone and needed a second `no-restricted-syntax` rule.
- `TENANT_SCOPED_MODELS` extends §8.3's own illustrative list with `membership`, `customerNote`, and `businessHours`, which §12's authoritative model table marks tenant-owned but that illustrative list omitted. `Membership` is deliberately tenant-scoped per §16.4's own wording ("`User` outside of `Membership`" is control-plane) — this is what let `/api/admin/users` be rebuilt on `Membership` instead of the legacy `Admin` table.
- `requireAuth()` now resolves a full `TenantContext` from either a JWT (→ `User` → earliest-created `Membership`, since this codebase has no business-switcher yet) or an `X-API-Key` header (→ `keyPrefix` lookup → `keyHash` compare → the key's own `businessId`/role). `/api/auth`'s setup/login actions were rewritten to create/authenticate against `Business`+`TenantPlacement`+`User`+`Membership` directly — Phase 1 had migrated the data but never cut the login path itself over from `Admin`, so this was a real gap Phase 2 had to close for login to work at all post-Phase-1. `generateToken()`/`verifyToken()` now carry only `{ userId }`, per §14.4.
- `src/middleware.ts` does not exist in this codebase — Phase 0 had already adopted this fork's `src/proxy.ts` convention (`node_modules/next/dist/docs/.../proxy.md` — Next 16 deprecated and renamed `middleware`). §46.2 task 5's rewrite target was `src/proxy.ts`; its secure-by-default allowlist logic now shares one list (`src/lib/public-api-paths.ts`) with the new route-auth-coverage static check so the two can't drift apart.
- All ~68 route files, plus their directly-called `src/lib/**` service modules, are migrated to the explicit-`ctx` service pattern (§16.2), organized as one `src/lib/<module>/service.ts` per resource. Batches followed the task list's order (customers → conversations → tickets → knowledge → team → channels → webhooks → automation/campaigns/flows → admin/settings), each with its own isolation test file written and run before moving to the next.
- **Scope boundary, not an oversight — but the first-pass Phase 2 report understated its own risk.** The AI chat/tool-execution pipeline (`src/lib/ai/engine.ts`, `ai/semantic-search.ts`, `ai/tools.ts`, `customer-resolver.ts`), the channel-adapter integrations it's driven by (`channels/{email,phone,sms,telegram,whatsapp}.ts`, `twilio-verify.ts`), and `/api/settings` were correctly identified as depending on Phase 1's `getDefaultBusinessId()` shim, and correctly identified as belonging architecturally to Phase 4/5/6 (`ToolPolicy`/`ExecutionPrincipal`-based AI authorization, `ChannelAdapter` contracts, `AIProviderRegistry`). But the report then also claimed "a second business is safe to onboard externally" without separately verifying that these still-shimmed paths *fail closed* for that second business rather than *silently executing against the Default Business on its behalf*. They did not fail closed. A **Phase 2 runtime-isolation audit** (a follow-up pass, same phase, before Phase 3 began) traced every externally reachable call chain through these files and found two real cross-tenant vulnerabilities, not just an architectural scope boundary: `/api/settings` let any authenticated business's admin read and overwrite the Default Business's live AI/SMTP/IMAP/Twilio credentials (`assertDefaultBusinessOnly` was entirely absent), and `/api/chat` silently wrote a non-default business's conversations/messages under the Default Business's id while merging *every* business's active knowledge entries into one shared AI prompt (`ai/engine.ts`'s `getKnowledgeBase()` queried `knowledgeEntry.findMany()` with no `businessId` filter at all, and `customer-resolver.ts` matched/updated customer records purely by contact-info collision with no tenant scoping). Both are now fixed: `ai/engine.ts`, `ai/tools.ts`, `ai/semantic-search.ts`, and `customer-resolver.ts` are structurally `ctx`-aware everywhere a `TenantContext` is available (raw-client import removed entirely from `customer-resolver.ts`); `/api/chat`, `/api/settings`, `/api/knowledge/test`, and the WhatsApp/email connect-disconnect actions each call a new, explicit, fail-closed guard — `assertDefaultBusinessOnly(ctx, featureLabel)` — before touching the still-global `Settings`-derived config, throwing `AppError(501, "NOT_YET_SUPPORTED", ...)` instead of proceeding. The channel adapters themselves (`channels/{email,phone,sms,telegram,whatsapp}.ts`) have no caller identity at all — no JWT, no API key, just an inbound provider webhook — so there is no "wrong business" to guard against yet; they now construct their one, explicit, documented `TenantContext` via a new `getDefaultBusinessContext()` (distinct from a silent fallback: the choice is visible at the call site, not buried inside `chat()`/`resolveCustomer()`), and `getScopedPrisma(ctx)` still structurally enforces every query against that id. `twilio-verify.ts` needed no change — it validates an inbound webhook's HMAC signature against the one global Twilio auth token before any business identity is relevant at all, and never touches tenant-owned data. New coverage: `tests/security/two-business-runtime-isolation.test.ts` proves all of this against real Postgres — the Default Business and a second, ordinary business, exercising `/api/chat`, `/api/settings`, `/api/knowledge/test`, and WhatsApp connect/disconnect as the second business, asserting the 501/`NOT_YET_SUPPORTED` response *and* that no row was persisted under the Default Business as a side effect, *and* (for `/api/chat`) that the second business's knowledge never appears in the Default Business's AI prompt and vice versa. **Consequence: `src/lib/default-business.ts` is still not deleted**, but is now narrowed to exactly three exports with no other legitimate callers: `getDefaultBusinessId()` (used only by the two guards below, plus migration/seed scripts), `assertDefaultBusinessOnly()` (the fail-closed guard), and `getDefaultBusinessContext()` (the one remaining explicit, documented single-tenant-context construction, for genuinely-identity-less inbound channel webhooks). It must never again be called as an implicit substitute for a real `TenantContext` inside a function that also accepts one — the module's own header comment now states this. Whichever of Phase 5/Phase 6 lands first should delete it as part of converting its last remaining callers (the channel adapters).
- `/api/settings` (the legacy `Settings` singleton) is also left unconverted, matching Phase 1's own implementation record ("`Settings.aiApiKey` remains in the retained legacy `Settings` row ... Phase 4 must migrate it") — but, per the audit above, it is no longer reachable by a non-default business at all (`assertDefaultBusinessOnly` gates both `GET` and `PUT`). Every *other* route that used to read/write `Settings` or the legacy `Channel` model (`/api/channels/**`, `/api/business-hours`) was cut over to its Phase-1-built replacement (`ChannelConnection`, per-business `BusinessHours`) in this phase — `/api/settings` itself is the one exception, deferred to Phase 4 by name, now fail-closed rather than silently cross-tenant.
- **"A second business is safe to onboard externally" (§45.2) is now proven, not inferred.** Every externally reachable Phase 2 path either operates on the authenticated caller's own `TenantContext` (the ~68 migrated routes from the bullet above, plus, after the audit, standard CRUD confirmed to persist the caller's own `businessId` directly rather than by response-shape inference alone) or fails closed with `501 NOT_YET_SUPPORTED` for a caller that isn't the Default Business (`/api/chat`, `/api/settings`, `/api/knowledge/test`, WhatsApp/email connect-disconnect) — never silently executing against the Default Business's data. What remains genuinely unavailable to a second business until Phase 4/5/6 (by design, documented, fail-closed, not a gap): AI chat/knowledge-testing (needs a real per-business `AIProviderRegistry`, Phase 4), the legacy `Settings` singleton generally (Phase 4), and the shared-process WhatsApp session / Twilio-phone / other inbound channel adapters (need real per-business `ChannelConnection` resolution, Phase 5) — a second business can be onboarded and can safely use every other migrated resource (customers, conversations, tickets, knowledge base CRUD, team, webhooks, automation, admin) today, with zero risk of touching or being served the Default Business's data.
- The dashboard homepage (`src/app/(dashboard)/page.tsx`, a React Server Component) queried conversation/ticket/message counts with no tenant filter at all — every business's stats and recent conversations were visible on every other business's dashboard. Not named in §46.2's task list (it predates the route-handler-focused "Current code involved" list), but treated as in-scope since it is exactly the class of leak this phase exists to close. Fixed via a new `getTenantContextFromCookies()` (`route-auth.ts`), the Server-Component equivalent of `requireAuth()`'s cookie branch.
- `ApiKey` role capping (§9.1/§9.4 — a key can never be `"owner"`) extends naturally to `Membership`-based team-member creation: `/api/admin/users` can grant any RBAC role except `"owner"` through its generic invite flow, matching the same "no privileged role through a generic/leakable path" reasoning.
- §33.4's seven named test cases: items 3 (database relational tenant protection) and 4 (raw Prisma escape) are this phase's own gates and are both covered (`tests/repository/composite-fk-bypass.test.ts`; `tests/security/raw-prisma-lint.test.ts`, extended to dynamic imports). Item 5 (API-key database compromise) was Phase 1's storage-only test; this phase adds `tests/security/api-key-authentication.test.ts`, exercising the real hash-compare authentication path end-to-end, including cross-business rejection. Items 1, 2, 6, 7 remain correctly gated to Phases 5/6 and are not claimed here.
- §14.2's CI-enforced "every route is public-allowlisted or calls `requireAuth`" check did not exist before this phase; added as `tests/security/route-auth-coverage.test.ts`, walking every `src/app/api/**/route.ts` file, with its own deliberate-violation pair.
- The runtime-isolation audit's own new suite, `tests/security/two-business-runtime-isolation.test.ts` (real Postgres + real auth + real `default-business.ts`, not the global mocks): the Default Business and one ordinary second business both hit `/api/chat`, `/api/settings`, `/api/knowledge/test`, and WhatsApp connect/disconnect; the second business gets `501 NOT_YET_SUPPORTED` on every one, verified by querying Postgres directly afterward that no row was persisted under the Default Business as a side effect of the rejected call (not just the HTTP status), that the AI provider was never invoked on the second business's behalf, and that the Default Business's own successful calls never leak the second business's knowledge-base content into its AI prompt. Also covers a second business's API key hitting `/api/chat` (resolves to its own context, still correctly fail-closed there — proving the guard checks identity, not the auth mechanism) and a plain CRUD route (`/api/customers`) persisting the caller's real `businessId`, not the Default Business's.

### Implementation record (Phase 4 complete)

Phase 4 is implemented and complete, including its one live-credential acceptance criterion. This is a record of concrete findings from that implementation, not a revision to the architecture above.

- `AIProvider`/`EmbeddingProvider` (§21.1/§21.5) are finalized at `ai/providers/types.ts` per §46.3's own deferral, informed by a real second implementation as intended: `OpenAIProvider`/`AnthropicProvider` (generation) and `OpenAIEmbeddingProvider` (embedding), each a thin wrapper translating to/from the provider-agnostic shape and mapping SDK errors to `AIProviderError` with an honest `retryable` flag. `OllamaProvider` is an honest stub. `@anthropic-ai/sdk` was added as a new dependency. One deliberate refinement over §21.1's illustrative sketch: `AIProviderRegistry.get(name, credential)`/`EmbeddingProviderRegistry.get(name, credential)` take the resolved credential as an explicit parameter and construct a fresh, credential-bound provider instance per call, rather than one long-lived singleton per name — necessary because two businesses selecting the same provider name almost always hold different API keys (§10.3/§16.5's explicit-secret-resolution discipline).
- `BusinessConfig` gains `aiCredentialRef`/`embeddingCredentialRef` (nullable, opaque `SecretResolver` refs, mirroring `ChannelConnection.credentialRef` — §7.7) via an additive migration, plus a new tenant-scoped `AIInteractionLog` table (composite FK to `Conversation`, per §8.4) for the usage-persistence decision named in task 8. Typed per-provider credential schemas live at `ai/providers/credentials.ts`, separate from `secrets/credential-schemas.ts` (a different namespace — provider name, not channel type).
- `ai/config.ts`'s `resolveAIConfig()`/`resolveEmbeddingConfig()` are the real per-business configuration boundary `Settings.aiApiKey` was deferred to this phase for. Precedence, made explicit and tested (not a second silent source of truth): `BusinessConfig`'s own credential first, for any business; else, for the Default Business only, the legacy `Settings` singleton — but only while `BusinessConfig.aiProvider` hasn't diverged from what that legacy row itself currently says. This comparison-based check (not "is `aiProvider` set") was a correction made during implementation: Phase 1's own migration script (`splitSettingsIntoBusinessConfigAndChannelConnections`) already copies `Settings.aiProvider`/`aiModel`/`maxTokens`/`temperature` verbatim into the Default Business's `BusinessConfig` at migration time (it could not copy `aiApiKey`, which is exactly the gap this phase closes) — a naive "aiProvider is unset" check would have made a genuinely-migrated production system's fallback unreachable, while a naive "aiProvider is set" check would have masked the opposite failure mode (an admin explicitly switching provider without a new key silently resolving the old provider's leftover key). A legacy `aiProvider: "claude"` value (the pre-Phase-4 setup wizard's stored value) normalizes to `"anthropic"`, matching `AIProviderRegistry`'s key.
- `knowledge/semantic-search.ts`'s `searchKnowledgeBase()`/`indexKnowledgeEntry()` are rewired onto `EmbeddingProvider` (resolved via `resolveEmbeddingConfig()`) instead of a direct `fetch("https://api.openai.com/v1/embeddings")` call — verified by code review (zero remaining `fetch(` calls in that file) and by tests asserting the embedding provider is invoked and no direct fetch occurs. The entries query was already tenant-scoped via `getScopedPrisma(ctx)` before this phase; what changed is the embedding side. The embedding cache key is now tenant- and provider-scoped (`embedding:${businessId}:${providerName}:...`), closing a latent cross-tenant cache-sharing gap the previous global key would have had once per-business embedding config existed. `knowledge/retriever.ts`'s `knowledgeRetriever` (the `KnowledgeRetriever` default implementation, §22.1, finalized in this phase) wraps it with a default limit of 8. `ai/engine.ts`'s `getKnowledgeBase()` and `knowledge/retrieval.ts` are deleted.

The characterization suites (`chat-flow.test.ts`, `whatsapp-inbound.test.ts`) keep their original assertions unchanged, with only their config-source mocks updated to the new `BusinessConfig`-first, legacy-`Settings`-fallback resolution path. The release-level browser regression suite: rerun it, in full, before any major release or milestone tag, and after any change that touches routing, authentication, channels, the worker, or the widget. It complements, and never replaces, the automated suites (unit, contract, isolation, `tests/e2e/mvp-acceptance.test.ts`). Earlier the same day: the knowledge-indexing follow-up, all 16 journeys including the new J04b, run from a fresh database with the local LLM stand-in, on a production build with the worker as a separate process. Those fixes are now committed (`fix(dashboard)`/`fix(onboarding)`, 2026-09-30), and the 2026-09-30 run is the first against a clean tree.

**Running it.** `scripts/acceptance/run-all.sh` runs the full suite in its real dependency order (not raw numeric order — J03/J03b's cross-tenant attack surface needs data J04/J05/J06b/J08/J11 create first; see the script's own header comment) and exits non-zero the moment any journey's assertions fail. Every journey script asserts its own acceptance-critical outcomes via `lib.cjs`'s `assert()`/`finish()` and fails loudly (non-zero exit) rather than only printing evidence for a human to read. Chromium is resolved automatically (`CHROMIUM_PATH`, else `puppeteer`'s own cached build) and `sql()` targets whatever database `ACC_DB` names — never a hardcoded database — so the harness carries no hidden dependency on any previous run's state.

**Topology (production-equivalent; record any deviation).** A throwaway database on the compose Postgres (`CREATE DATABASE ziyrak_acceptance`, then `prisma migrate deploy` — a fresh install has *no* Default Business, deliberately, so fresh-install behaviour is exercised); a production build made with `NEXT_PUBLIC_APP_URL=http://localhost:3100` (Next inlines it); `next start` on :3100 and `npm run worker` as separate processes; two "customer websites" on other origins (:4020 Business A, :4021 Business B) so CORS and the origin allowlist are genuinely cross-origin. `ACC_DB=<url> scripts/acceptance/start-all.sh` starts everything; `scripts/acceptance/run.sh jNN-….cjs` runs one journey (they must run in order — J01 creates the businesses the rest use). Give each persona its own `X-Forwarded-For`, as a reverse proxy would: the limiter is in-memory and keyed by IP, and without proxy headers every client shares one bucket (§Phase 8).

**Browser tooling.** Scripts drive a real headless Chromium through `puppeteer-core` (`CHROMIUM_PATH` to override) with separate browser profiles per business owner and isolated contexts per anonymous visitor. This is the agent using browser tooling directly (case 1 above); it is a scripted browser, not the interactive computer-use browser — a session that has the latter should use it for the exploratory pass and keep these scripts for the repeatable one. UI steps go through the real UI wherever a UI exists; the few steps done through the authenticated API or the database are marked **[API]** / **[DB]** below.

**LLM.** With a live provider key, use it and drop `OPENAI_BASE_URL`. Without one, `scripts/acceptance/llm-standin.cjs` is a local OpenAI-compatible endpoint that answers *only from what is in the prompt it receives* and logs every prompt to `.work/llm-requests.jsonl`. It proves what the product contributes — retrieval, tenant scoping, prompt assembly, tool wiring — **not model quality**; a run that used it must say so, and the live-model criteria stay open.
