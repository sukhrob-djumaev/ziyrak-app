# L4.1 catalog and entitlement foundation — design (2026-10-27)

Status: **proposal for independent review; no code yet.** Governs `docs/billing-and-entitlements-spec.md` (B01, B02-view, B07, B08, B10). Provider-neutral: no payment provider, no checkout, no price collection (L4.2/L5).

## Split
- **L4.1a** — capability registry, catalog schema and lifecycle (draft → preview → published immutable → archived), platform console + audit, baseline bundle and migration (B01, B10 part).
- **L4.1b** — workspace purchase records, entitlement resolver with provenance, central enforcement (web services, worker), owner offer/usage view, platform spend ceilings, trial-abuse limits (B02 view, B07, B08 part).
Each part is its own PR with its own browser run.

## 1. Capability registry (code-owned, `src/lib/billing/capabilities.ts`)
A typed constant table; the only place a capability exists. Entry: `{ key, label, kind: "boolean" | "limit", unit?, period?: "none" | "utc_month", combine: "union" | "max" | "sum", enforcedBy: string[] }`.

Initial keys (only things the product already enforces or can enforce centrally in L4.1b):
| key | kind | combine | enforced at |
| --- | --- | --- | --- |
| `channel.webchat` | boolean | union | channel connect, widget inbound |
| `channel.whatsapp_cloud` | boolean | union | channel connect, Meta inbound/outbound |
| `ai.generation_tokens` | limit tokens/utc_month | sum | `reserveAllowance` |
| `ai.embedding_tokens` | limit tokens/utc_month | sum | `reserveAllowance` |
| `seats.members` | limit count | sum | invitation create/accept |
| `automation.rules` | boolean | union | rule create, rule execution |
| `webhooks.outbound` | boolean | union | webhook create, delivery job |
| `data.export` | boolean | union | `/api/export` |
`enforcedBy` is a list of named call sites used by a test that fails when a published-able capability has no enforcement site. Unlisted/unimplemented capabilities (Email, Phone, Keyword Alert, extra connections) are **not in the registry**, so no catalog item can reference them.

## 2. Catalog schema (additive migration; control-plane tables, no `businessId`)
```
CatalogItem   id, key (unique, kebab), kind "bundle"|"addon", createdAt
CatalogVersion id, itemId→CatalogItem, version Int, state "draft"|"published"|"archived",
              name, description,
              grants Json   -- [{capability, amount?}] validated against the registry
              priceMinor Int?, currency String?, interval "month"|"year"?   -- TEST/display prices; nullable on drafts
              quantityMin Int @default(1), quantityMax Int @default(1)
              requires String[]  (item keys), excludes String[] (item keys)
              availableFrom/availableTo DateTime?
              rev Int           -- optimistic concurrency, bumped on every draft edit
              createdBy, publishedBy?, publishedAt?, archivedAt?, createdAt
              @@unique([itemId, version]);   at most one draft per item (partial unique index)
CatalogAudit  id, versionId?, itemId, actorUserId, action ("draft.create|draft.update|publish|archive|assign"), reason, diff Json, createdAt
```
Rules (service, in one transaction with the audit row):
- A published/archived version is immutable (DB trigger rejects UPDATE of grants/price/quantity/requires/excludes/name when state ≠ draft; only `state`/`archivedAt` may change, published→archived only).
- Edit changes a draft only, with `rev` compare-and-set (409 on stale).
- **Publish** validates: every grant key exists in the registry; boolean grants have no amount, limit grants have integer amount 1..registry max; `quantityMin ≤ quantityMax`; `requires`/`excludes` reference existing items and are not self/cyclic/contradictory; price present with ISO currency and interval; `availableFrom < availableTo`. Failure → 400 with the list; nothing published. A new item's first publish creates version 1; later versions are new drafts copied from the latest published.
- **Archive** stops new assignment/sale only; existing purchases untouched.
- Preview: `previewVersion(id)` returns the validated grants, composed example for a workspace with that version alone and with each other published item (shows combine results), and the list of workspaces currently holding any version of the item (count, ids for super-admin).

## 3. Platform console (L4.1a)
`/api/platform/catalog` (GET console; POST actions `create_item`, `save_draft`, `publish`, `archive`) mirroring `/api/platform/ai-service`: `requireAccountAuth`, same-origin + JSON checks, rate limit, `withPlatformControl(token, "super_admin")`, `writePlatformAudit` + `CatalogAudit`, reasons mandatory, secrets none. Page `src/app/(auth)/platform/catalog/page.tsx`. Operators and tenants have no path. Catalog edits need no redeploy.

## 4. Baseline and migration (B10)
The migration seeds one published bundle `legacy-baseline` (v1) granting exactly today's behaviour: both channels, automation, webhooks, export, AI limits equal to the current allowance defaults (500 000 / 1 000 000), `seats.members` large (1000). Price null (not sold; `availableTo` = past so it is not purchasable). `PlatformSetting default_bundle = legacy-baseline` is what newly provisioned workspaces receive until L4.2 chooses a commercial default. Nothing is billed, deleted or narrowed for any existing workspace.

## 5. Purchases and resolver (L4.1b)
```
WorkspacePurchase id, businessId→Business, versionId→CatalogVersion, quantity Int,
                  source "baseline"|"manual_test"|"provider",   -- "provider" is written only by L5
                  state "active"|"ended", startsAt, endsAt?, reason, createdBy, createdAt
EntitlementAdjustment id, businessId, capability, amount?(for limits)/grant bool, expiresAt (required), reason, createdBy
```
`resolveEntitlements(businessId, now)` is a pure function over (registry, active purchases with versions, unexpired adjustments) returning `{ capability → { granted | limit, provenance: [{purchaseId|adjustmentId, versionId, amount}] } }`, applying each key's `combine` rule; overlapping grants of a boolean key stay granted while any source remains; sums are explicit; adjustments expire; an unknown/retired key in an old version is ignored with a recorded warning, never granted. No client input.
Platform actions (super-admin, audited): `assign_version` (source `manual_test` or `baseline`), `end_purchase`, `set_adjustment` (expiry mandatory, max 90 days).

## 6. Enforcement (L4.1b)
`assertEntitled(ctx|businessId, capability)` / `entitledLimit(businessId, capability)` in services and in worker handlers at execution time (never only navigation). Resolver result cached per process ≤ 15 s keyed by a `Business.entitlementRev` integer bumped by every purchase/adjustment write (cache validated against the DB value on each privileged operation: one indexed read), so revocation takes effect within one operation, not a TTL. Failure → `403 ENTITLEMENT_REQUIRED` with capability key, safe for the UI. Entitlements never widen role, channel scope or `requiresHumanApproval`: the check is an additional AND; `ToolPolicy` is not consulted or altered. Delayed jobs re-resolve at execution. Account security, recovery, billing status read and data-rights routes are exempt by explicit list.
`reserveAllowance` takes its limit from `ai.*_tokens` when the workspace has purchases, else the existing row (unchanged for workspaces without purchases, which after migration is none: all hold the baseline).

## 7. Platform-wide limits (L4.1b, B08 part)
```
PlatformLimit key (pk), value Int, updatedBy, updatedAt
   monthly_generation_tokens_ceiling, monthly_embedding_tokens_ceiling   -- across all workspaces, UTC month
   max_owned_workspaces_per_user, max_new_workspaces_per_day            -- trial/free-abuse
```
Reservation checks the ceiling under an advisory lock taken before the per-workspace row lock (fixed order to avoid deadlock); signup/provisioning checks the two abuse limits in its transaction. Defaults are permissive-but-finite and recorded; super-admin edits are audited.

## 8. Owner view (L4.1b, B02 view part)
`GET /api/billing/offer` requires `business:billing` (owner only): current purchases with provenance, effective capabilities, usage vs limit (from reservations, labelled "estimate, not an invoice"), published add-ons not yet held. Page `/billing` visible only with the permission (nav item with `requires: "business:billing"`; route guard). No mutation in L4.1 (no checkout).

## 9. Acceptance mapping and tests
- B01: UI journey publishes a bundle and an independent add-on (test prices), changes a price by new version, archives; assigned workspace keeps the old version's terms; unknown capability / contradictory requires rejected; combine/overlap/retirement unit tests.
- B07: entitlement removal observed by a delayed worker job and an open request; entitlement never grants a role or removes approval.
- B08: concurrent reservations across two workspaces hold the platform ceiling; adjustment expiry cannot double count.
- B10: migration test on a database with existing workspaces: every workspace has the baseline purchase, behaviour unchanged, no extra rows deleted.
- Tenant isolation: owner view returns only the caller's workspace; platform tables unreachable from tenant APIs (scope-schema unchanged for control-plane models).
- Independent security review on both PRs (authz, tenant isolation, payments-adjacent).

## Open points for the reviewer
1. DB trigger vs service-only immutability for published versions. 2. `entitlementRev` read per privileged operation cost. 3. Whether `seats.members` enforcement at invitation *accept* is race-safe without a lock. 4. Advisory-lock ordering for ceilings.

# Revision 2 (after independent design review, 2026-10-27) — overrides the sections above where they differ
Review findings are data, each verified against the code before adoption.

1. **AI limits stay with the existing allowance row.** `ai.generation_tokens` / `ai.embedding_tokens` are removed from the registry. `WorkspaceAiAllowance` (mode, status, limits, set by `set_allowance`) remains authoritative, so customised workspaces and `pending_verification` are unchanged. L4.1b adds only the **platform-wide ceiling** (workspace row lock first, global lock last and brief, new index `(kind, periodStart, state)` on `AiUsageReservation`). A catalog-driven AI quantity is deferred to L4.2/L5 with an explicit migration of the row.
2. **Baseline and B10 move to L4.1b** with `WorkspacePurchase`. A helper `ensureBaselinePurchase(tx, businessId)` is called inside `provisionBusiness`'s transaction, by `prisma/seed.ts`, `tests/helpers/tenant-fixtures.ts` and the migration-step scripts; a test asserts every workspace holds exactly one active bundle purchase. Enforcement is **fail-closed** for a workspace with no purchase (after the helper exists everywhere). No `PlatformSetting` table: the default bundle is the item key `legacy-baseline`, a code constant until L4.2. The baseline is created by migration with `createdBy` null and is exempt from the price-required publish rule and from `availableTo`.
3. **Tenant-isolation classification:** every new model gets a `SCOPE_SCHEMA` entry and is added to `CONTROL_PLANE_ONLY_MODELS` (`resource-query.ts`), `Business` gains the new relations/scalars, and `tests/setup.ts` mocks them.
4. **No `Business.entitlementRev`, no cache.** The resolver reads live (one indexed join per privileged operation). Writes to purchases/adjustments that remove capability take `lockTenantWrites(tx, businessId)` (work-lifecycle.ts) and lock order is platform control lock → workspace fence; any raw SQL file is added to the inventory test.
5. **One active bundle per workspace** (service-enforced + partial unique index); add-ons combine by their registry rule (`sum` only for quantities). No double allowance by overlap.
6. **Seat limit** is checked in `createInvitation` and inside `acceptInvitation`'s transaction after `lockTenantWrites`, counting existing members once. `end_purchase` takes the same lock.
7. **Enforcement sites (verified names):** Web Chat `createWebChatConnection/updateWebChatConnection/rotateWebChatToken`; WhatsApp `upsertByType/performAction`, `prepareMetaCloudConnection`; automation rule service `create/update` and `evaluateRules/applyAutomationActions`; webhooks `/api/webhooks`, `/api/webhooks/test`, AI tool `trigger_webhook`, `retryDelivery`, job `deliver-webhook` (permanent failure, no retry loop, when denied); export `/api/export`; seats `createInvitation/acceptInvitation` (`src/lib/platform/admin-users/invitations.ts`). **Inbound customer messages are never gated** (spec: preserve incoming messages and handoff). Tools declare `requiredCapability`, checked in `ToolRegistry.isAvailable` and `runAndRecord`; an approval for a tool whose capability was lost ends failed/cancelled and never executes.
8. **L4.1a scope (this PR):** capability registry (boolean capabilities only: `channel.webchat`, `channel.whatsapp_cloud`, `automation.rules`, `webhooks.outbound`, `data.export`; `seats.members` limit added in L4.1b with its enforcement); `CatalogItem` + `CatalogVersion` (grants, price/currency/interval, rev, state); DB trigger making non-draft versions immutable except `published→archived` (plus code CAS on `rev`); publish validation; one `PlatformAccessAudit` row per action via `writePlatformAudit` (no separate CatalogAudit); platform console API + page; tests. **Cut from L4.1a:** availability dates, quantity bounds, requires/excludes, composition preview, holders list, default-bundle setting. B01 closes in L4.1b (needs purchases and the resolver); B07/B08/B10 likewise. Rollback of L4.1b is app-only: tables are additive and unused by older code.

# Revision 3 (L4.1b review, 2026-10-28)
- **Split:** platform-wide AI spend ceilings and trial/abuse limits move to **L4.1c** (B08 part); L4.1b delivers purchases, resolver, enforcement, owner view, console assignment.
- **Switching off is never gated:** turning a Web Chat widget, webhook or automation rule off, rotating a Web Chat token, deleting and reading history stay available without the capability.
- **Lost `automation.rules`:** `auto_reply` rules keep firing (fixed wording must never be replaced by a new AI answer or new spend); routing/tagging/alerts stop.
- **Baseline everywhere:** an AFTER INSERT trigger on `Business` gives every new workspace the baseline package even from an older app version during a rolling deploy; the application helper stays and is idempotent. The baseline item key is protected from console archive/new-version/re-create.
- **Owner view** shows no admin-internal reason text.
- **Open product/legal question (owner):** bulk `/api/export` is gated by `data.export`; the per-customer GDPR export/delete routes are not gated. Whether a workspace's bulk export of its own data must remain available after a downgrade is not decided here.
