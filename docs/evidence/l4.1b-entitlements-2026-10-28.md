# L4.1b purchases, entitlement resolver and enforcement — implementation record (2026-10-28)

PR #55 merged as `081c35c`; verified head `d70e631`. Design: `docs/l4.1-catalog-entitlements-design.md` (Revisions 2 and 3). Provider-neutral; no money is collected.

## Delivered
- `WorkspacePurchase` / `EntitlementAdjustment` (additive migration `20261028000000_l4_1b_purchases`): CHECKs, one active row per version; the published `legacy-baseline` bundle (today's access, price 0, `seats.members` 1000) is seeded and given to every existing workspace; an AFTER INSERT trigger on `Business` and the idempotent `ensureBaselinePurchase` give it to every new one (provisioning, seed, migration steps, fixtures).
- Live resolver (`src/lib/billing/entitlements.ts`): boolean union, explicit sum for quantities, one bundle plus add-ons, adjustments expire within 90 days, retired keys never granted, provenance, no cache.
- Enforcement added after (never instead of) permission checks: Web Chat and Meta WhatsApp setup, automation rule save and execution, webhooks (routes, test, retry, AI tool, delivery job), workspace export, member seats (invitation, and acceptance under the workspace write fence). Tools carry `requiredCapability`, checked when offered and again at execution, so a pending approval cannot run a tool whose capability was lost. Inbound customer messages are never gated; switching off, token rotation, deleting and reading history stay available; fixed `auto_reply` rules keep firing when automation is lost.
- Owner `Plan & usage` (`/billing`, `GET /api/billing/offer`, owner-only `business:billing`); super-admin console assignment/end/adjustment with mandatory audited reasons; the baseline item is protected from console archive/new version.
- Package refusals show the server's explanation, not the role message.
