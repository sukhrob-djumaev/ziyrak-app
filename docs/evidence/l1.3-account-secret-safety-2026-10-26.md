# L1.3 account and secret safety — implementation record (2026-10-26)

Status: implemented on `fix/l1-3-account-secret-safety` (draft PR #38). Combined-build browser run NOT run (see blocker in the L1.2 record); CI is the verifier so far.

## Changes
- F03: `completePasswordReset` claims the token, changes the password and moves the session cutoff in ONE transaction (`consumeAccountToken(..., tx)`); failure leaves the link usable. Tests: `tests/repository/password-reset-atomicity.test.ts` (failure injection, concurrency, burned-link case).
- F09: `EnvKeySecretResolver` discovers any `SECRET_KEY_V<n>` (sparse / V1 retired), optional `SECRET_KEY_ACTIVE_VERSION`; `reencryptMfaSecrets()` moves stored second-factor secrets onto the active key before an old key is retired. Tests: `tests/unit/secret-key-rotation.test.ts`.
- F16: central redaction in `src/lib/observability/logger.ts` (sensitive keys at any depth; bearer/API-key/URL-credential/JSON-shaped/bot-token strings), benign look-alikes kept; `SECURITY.md` no longer overclaims. Tests: `tests/unit/logger-redaction.test.ts`.
- Cookie mutation policy: `src/lib/http/mutation-guard.ts` in `src/proxy.ts` for cookie-authenticated `/api/**` writes and for `/api/auth` POSTs (login CSRF): same-origin via Fetch Metadata/Origin, JSON when a body is sent. All dashboard fetches that send a body already set JSON content type (checked by script).
- Signup ceilings: per address 10/h and platform-wide 200/h (`ZIYRAK_SIGNUP_PLATFORM_PER_HOUR`) before any provisioning (`tests/repository/signup-abuse.test.ts`).
- Platform second factor: RFC 6238 TOTP (`totp.ts`, RFC vectors), encrypted secret + hashed (HMAC, 80-bit) single-use recovery codes, replay protection, per-account attempt budget (successes reset it), login challenge, `mfa` session claim, enforcement inside `currentAuthority` (also checks `sessionsValidAfter`), self-service enrollment `/api/auth/mfa`, audited super-admin reset (`reset-mfa`). Migration `20261026010000_l1_3_platform_mfa`.

## Open (not closed by this task)
- MFA defaults to `optional` (`ZIYRAK_PLATFORM_MFA=required` enforces). There is no enrollment UI, so `required` would lock operators out; a launch gate: ship the UI + browser journey, then set `required` in production.
- In `required` mode whoever holds an unenrolled account's password can enroll first; needs a one-time enrollment proof issued by a super admin (product decision).
- `TRUSTED_PROXY_HOPS` is still only logged when unset: client-address limits (auth, signup ceilings) can be spoofed without a trusted edge. Platform-wide signup ceiling can be exhausted from many addresses (deployment contract, L2.1).
- Per-account TOTP budget can lock out an operator whose password is known (8 tries/15 min); no alerting yet.
- Existing browser journeys j20/j22 sign in platform accounts; optional mode keeps them valid but they have not been rerun on this branch.
